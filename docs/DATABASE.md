# NexTap database specification

Status: Approved. Documentation only; no implementation is authorized.

## Purpose and authority

This document defines the physical persistence design for the first release. It follows [vision.md](vision.md), especially sections 3–5, 7–12, 17–25, 33 and 43, and the 47-answer [accepted-decision ledger](../.atomic/recovery/accepted-decisions.json). The ledger overrides stale unresolved wording in earlier drafts. Companion contracts are in [PRODUCT_SPEC.md](PRODUCT_SPEC.md), [ARCHITECTURE.md](ARCHITECTURE.md), [FLOWS_AND_API.md](FLOWS_AND_API.md), and [SECURITY_AND_EDGE_CASES.md](SECURITY_AND_EDGE_CASES.md).

No application, migration, provider account, runtime, backup, restore, or inventory workbook exists in the repository. This is documentation only. Where the ledger leaves an engineering detail open, this document labels a proposed implementation default; a default is not a new product or security decision.

## Settled database boundaries

- PostgreSQL on Supabase is the system of record. Internal primary keys are UUIDs; printed Card IDs are separate public tokens.
- Only NexTap Admin operates the v1 system. A Business has no owner-account foreign key.
- Cards are `inactive` or `active`; Businesses are `disabled` or `enabled`. Assignment and activation are separate.
- An Active Card may be assigned to a Disabled Business, but public resolution requires an Active Card, a current assignment, and an Enabled Business.
- Deactivation preserves assignment. Assign/reassign requires Inactive and leaves it Inactive. Unassign clears assignment and leaves the Card Inactive. Card IDs and Businesses are not hard-deleted or reused in v1.
- `/c/{cardId}` renders directly. `/b/{slug}` is an independent route; historical slugs remain reserved aliases for the same Business.
- A Business has at most one of each built-in Section: `hero`, `contact`, `social`, `payments`, `location`, `hours`, `reviews`, and `custom_links`. A Link belongs to exactly one supported link-bearing Section. Repeated platform types are allowed with distinct labels.
- Phone, WhatsApp and email columns are canonical contact data. Contact buttons derive from those fields; generic Links cannot override them.
- Hours are a seven-day weekly schedule with an IANA timezone, closed days, or one or more intervals. There is no holiday calendar or calculated open-now value in v1.
- Payment and review entries are external destinations only. There are no payment, balance, transaction, scan, click, or Visitor-event tables.
- New Card tokens require at least 128 cryptographically random bits. Existing printed tokens are imported and stored exactly, without normalization or regeneration.
- Every new public request performs a fresh eligibility check before cache reuse. Public content cache keys include Business and content revision. Unknown eligibility fails closed.
- Expected edit versions reject stale writes. A successful mutation, required audit row, and required Card history row commit atomically.

## Identifier and common-column conventions

All tables use `uuid` primary keys generated by PostgreSQL (`gen_random_uuid()`) except the slug registry, idempotency records, and other relations where a composite key is useful. Timestamps use `timestamptz` in UTC. Application writes use server/database time, not client-provided timestamps. Mutable aggregate rows use a nonnegative `bigint edit_version` starting at `1`; every successful update of that aggregate increments it exactly once.

The following columns are present on mutable tenant rows unless the table description says otherwise:

- `id uuid primary key`.
- `created_at timestamptz not null default now()`.
- `updated_at timestamptz not null default now()`.
- `edit_version bigint not null default 1 check (edit_version > 0)`.

`updated_at` and `edit_version` change together in the same transaction. The database, not an API payload, supplies `created_at`, `updated_at`, actor and lifecycle timestamps.

## Core tables

### `admin_members`

Supabase Auth owns credentials, password state and TOTP factors. This table is the application authorization projection:

| Column | Type | Constraint / meaning |
|---|---|---|
| `user_id` | `uuid` | Primary key and FK to the Auth user identity; no cascade from application tables |
| `status` | `text` | `active` or `disabled` |
| `created_at` | `timestamptz` | Required |
| `updated_at` | `timestamptz` | Required |

No public signup or Business-owner relation is represented here. A privileged request must check the current membership and MFA outside a stale browser-supplied role. Membership changes are audited.

### `businesses`

| Column | Type | Constraint / meaning |
|---|---|---|
| `id` | `uuid` | Primary key |
| `name` | `text` | Required; 1–120 Unicode characters after plain-text validation |
| `description` | `text` | Nullable; at most 1,000 Unicode characters |
| `phone` | `text` | Nullable canonical contact value |
| `whatsapp` | `text` | Nullable canonical contact value |
| `email` | `text` | Nullable canonical contact value |
| `address` | `text` | Nullable plain text; proposed default maximum 500 characters |
| `map_url` | `text` | Nullable canonical map destination; HTTPS, at most 2,048 characters, no embedded credentials |
| `directions_url` | `text` | Nullable canonical directions destination; same HTTPS validation |
| `google_reviews_url` | `text` | Nullable canonical Google Reviews navigation destination; same HTTPS validation; no rating/count data |
| `timezone` | `text` | Required IANA timezone name; default `UTC` when not supplied |
| `status` | `text` | `disabled` or `enabled`, default `disabled` |
| `content_revision` | `bigint` | Required, starts at `1`, increments on every public-representation mutation |
| `enabled_at` | `timestamptz` | Nullable; latest successful enablement time |
| `disabled_at` | `timestamptz` | Nullable; latest successful disablement time |
| common columns | — | As defined above |

`name` and a unique current slug are sufficient for enablement. Contact fields, Links, hours, location and images are optional. `content_revision` is deliberately distinct from `edit_version`: an administrative edit can change non-public operational metadata without changing the public representation, while any mutation that can alter the public projection increments `content_revision` in the same transaction.

Proposed implementation default: `address`, `map_url`, `directions_url` and `google_reviews_url` are the sole stored location/review content, mapped to API `address`, `mapUrl`, `directionsUrl` and `googleReviewsUrl` in [FLOWS_AND_API.md](FLOWS_AND_API.md#business-lifecycle-and-fields). They are not generic Links or Section settings. Null means no configured value/action; optional destinations need not accompany an address. Location projects address and its configured external actions only when its Section is enabled; Reviews projects the configured Google Reviews action only when its Section is enabled. No coordinates, embedded-map fetch, ratings synchronization or review-count persistence is introduced. Changes use the parent Business expected version, audit and atomic content-revision increment; clearing a value uses `null` under the API contract.

Recommended checks include status membership, `content_revision > 0`, and `enabled_at`/`disabled_at` consistency for the latest transition. No owner column is present.

### `cards`

| Column | Type | Constraint / meaning |
|---|---|---|
| `id` | `uuid` | Internal primary key |
| `public_token` | `text` | Not null, globally unique, immutable after insert; exact printed value |
| `status` | `text` | `inactive` or `active`, default `inactive` |
| `business_id` | `uuid` | Nullable FK to `businesses`; current assignment |
| `activated_at` | `timestamptz` | Nullable latest successful activation time; not history substitute |
| `deactivated_at` | `timestamptz` | Nullable latest successful deactivation time |
| `created_at` | `timestamptz` | Required; import/creation time |
| `updated_at` | `timestamptz` | Required |
| `edit_version` | `bigint` | Required, starts at `1` |

Use a binary-safe, case-sensitive uniqueness comparison for legacy tokens (proposed default: `text` with the database default binary collation, plus an application parser that does not case-fold). New-token encoding is a separate generated-token concern; it must provide at least 128 random bits. Do not impose a new-token regular expression on existing imports until a real inventory sample is inspected.

A check constraint enforces `status = 'active'` only when `business_id is not null`. Foreign-key deletion is `RESTRICT`; no business deletion is available. A Card cannot be active and unassigned. `activated_at` means the latest transition to Active and is nullable for never-activated Cards; `card_history` is authoritative for all prior activations.

### `business_slugs`

This is the global slug registry, not a denormalized Business field.

| Column | Type | Constraint / meaning |
|---|---|---|
| `slug` | `text` | Primary key; normalized registry value, unique forever |
| `business_id` | `uuid` | Required FK to `businesses` |
| `is_current` | `boolean` | Required |
| `created_at` | `timestamptz` | First reservation time |
| `retired_at` | `timestamptz` | Nullable; set when no longer current |

Proposed normalization default: trim Unicode whitespace, apply Unicode NFC, lowercase using an invariant ASCII-oriented slug grammar, and accept only `[a-z0-9]+(?:-[a-z0-9]+)*` with a 1–80 character bound. This is an implementation default pending compatibility review; it must never be applied to imported Card IDs. Reserved platform paths and redirecting slugs are rejected before insertion. A partial unique index on `(business_id) where is_current` permits exactly one current slug per Business. A transaction changes the current row and inserts the former slug alias together. Aliases redirect only after a fresh eligibility check and cannot be reassigned.

### `business_sections`

| Column | Type | Constraint / meaning |
|---|---|---|
| `id` | `uuid` | Primary key |
| `business_id` | `uuid` | Required FK |
| `section_type` | `text` | One of the eight registered types |
| `is_enabled` | `boolean` | Required, default `false` |
| `sort_order` | `integer` | Required, nonnegative |
| `settings` | `jsonb` | Required object, maximum 8 KiB encoded JSON |
| `settings_schema_version` | `smallint` | Required positive registry version |
| common columns | — | As defined above |

Unique `(business_id, section_type)` enforces one Section per type. The renderer owns the registered schema for each type; tenant data cannot provide HTML, scripts, components or arbitrary keys. `settings` contains presentation only, never canonical contact/location/review data, hours, Links, image paths or payment identifiers. Unknown fields, wrong value types and mismatched schema versions are rejected before persistence. Ordering is deterministic by `sort_order, id`; complete reorder commands update all configured rows, including disabled Sections, atomically.

Proposed implementation default: the initial registry uses `settings_schema_version = 1`, a default empty object `{}`, and the following complete allowlist. Every listed key is optional; omitted keys select the registered renderer default. Explicit `null`, nested objects/arrays and additional keys are rejected. `title` is trimmed NFC plain text with 1-80 Unicode scalar values when supplied; it labels a Section, not a competing Business name. `layout` and `style` accept only the literal values shown, never CSS, markup or executable component names.

| Section type | Allowed settings and renderer defaults | Authoritative content source |
|---|---|---|
| `hero` | `title` only; omitted title uses registered heading | Business name/description and current Logo/Cover references |
| `contact` | `title`; `layout: "buttons"` (default) | Business phone/WhatsApp/email; validated derived contact actions |
| `social` | `title`; `style: "icons"` (default) or `"buttons"` | Active member social Links |
| `payments` | `title`; `layout: "buttons"` (default) | Active member payment Links; external URLs only |
| `location` | `title` only | Business address, map URL and directions URL |
| `hours` | `title` only | Normalized weekly hours and Business timezone |
| `reviews` | `title`; `layout: "buttons"` (default) | Business Google Reviews URL; configured navigation only |
| `custom_links` | `title`; `layout: "buttons"` (default) | Active member custom Links |

Proposed byte-count default: validate the settings object before insertion, serialize it as compact UTF-8 JSON without insignificant whitespace, and require at most 8,192 bytes; measure serialized JSON, not PostgreSQL's internal `jsonb` storage size. Unicode counting, contact normalization and the 256 KiB non-multipart JSON-body ceiling follow the labeled defaults in [SECURITY_AND_EDGE_CASES.md](SECURITY_AND_EDGE_CASES.md#uploads-and-content-validation). The request ceiling is an API boundary, not a stored-row allowance. This registry completes implementation defaults within accepted bounds; it is neither a new Section type nor an external approval gate.

### `business_links`

| Column | Type | Constraint / meaning |
|---|---|---|
| `id` | `uuid` | Primary key |
| `business_id` | `uuid` | Required FK |
| `section_id` | `uuid` | Required FK to a link-bearing Section of the same Business |
| `link_type` | `text` | Registered type, such as `instagram`, `custom`, or `payment` |
| `label` | `text` | Required plain text, 1–80 characters |
| `normalized_label` | `text` | Server-maintained trimmed NFC/case-folded comparison key; never client-controlled |
| `url` | `text` | Required HTTPS URL, max 2,048 characters, no credentials |
| `icon_key` | `text` | Nullable registered icon key; no arbitrary icon URL |
| `is_active` | `boolean` | Required, default `true` |
| `sort_order` | `integer` | Required, nonnegative |
| common columns | — | As defined above |

A composite foreign key `(section_id, business_id)` references a unique `(id, business_id)` key on `business_sections`, preventing cross-tenant membership. A trigger or transaction-level count check enforces at most 50 Links per Business, including inactive Links and concurrent inserts. Generic link-bearing Sections are exactly `social`, `payments` and `custom_links`; `link_type` must be supported by the referenced Section. Repeated types are allowed with distinct labels under the normalization/default registry below. Contact-type Links are rejected because canonical contact columns own those actions; Location and Reviews use the canonical Business destination fields, not generic Links.

Link order is Section-local and deterministic by `sort_order, id`. A complete reorder contains every stored member Link of that Section exactly once, including inactive Links, with no omissions, duplicates, deleted or cross-Business/other-Section IDs. Proposed implementation default: assign consecutive nonnegative `sort_order` values from the supplied list in one parent-Business transaction. Section order likewise includes all configured Sections, including disabled ones. Public rendering filters to enabled Sections, then active member Links, retaining relative configured order; an inactive Link or a Link in a disabled Section never appears in another Section or a fallback list. Visibility toggles preserve stored membership and order. Required Link indexes and count checks apply to hidden content too.

Proposed Link registry default: `social` permits `instagram`, `facebook`, `tiktok`, `youtube`, `snapchat`, `linkedin` and `x`; `payments` permits `payment`, `instapay`, `vodafone_cash`, `paypal` and `stripe`; `custom_links` permits `custom`. Labels provide the specific action/platform wording and repeated types remain allowed. `icon_key` is null or one of those registered type keys; these are renderer-owned icons, not URLs, CSS classes or uploaded artwork. Unknown types/icons are rejected before persistence. Additional types/icons require a code/schema-registry change, not arbitrary tenant strings.

Proposed normalization default, aligned with Security: NFC-normalize and trim surrounding Unicode whitespace from user-facing text, count Unicode scalar values against the accepted bounds, and validate plain text before storage. Phone/WhatsApp values retain only an optional leading `+` and ASCII digits after permitted display separators (spaces, hyphens and parentheses) are removed; malformed values are rejected rather than interpreted as URLs. Email is trimmed/NFC-normalized with its domain lowercased and local part retained, then validated before generating `mailto:`. Empty optional text/contact fields normalize to null. Printed Card tokens are excluded from all normalization. For distinct active Link labels, use `(business_id, section_id, normalized_label)` uniqueness, where `normalized_label` is trimmed NFC label text with Unicode case-folding for comparison only; retain normalized display casing in `label`. Inactive duplicates may remain stored, but activation must pass the same uniqueness check. URL destinations are parsed/validated as HTTPS without credentials under Security's 2,048-scalar bound; never fetch supplied destinations server-side.

### `business_hours`

Hours are normalized rows rather than opaque JSON.

| Column | Type | Constraint / meaning |
|---|---|---|
| `business_id` | `uuid` | Primary key and FK |
| `timezone` | `text` | Required IANA timezone; normally copied from `businesses.timezone` |
| `updated_at` | `timestamptz` | Required |
| `edit_version` | `bigint` | Required |

`business_hour_intervals` stores zero or more intervals per day:

| Column | Type | Constraint / meaning |
|---|---|---|
| `id` | `uuid` | Primary key |
| `business_id` | `uuid` | Required |
| `weekday` | `smallint` | 0–6, ISO Monday through Sunday |
| `open_minute` | `smallint` | 0–1,439, local wall-clock minute |
| `close_minute` | `smallint` | 1–1,440; must be greater than `open_minute` |
| `sort_order` | `smallint` | Nonnegative deterministic order |

A day with no rows is closed. Multiple intervals are allowed; overlap and equal endpoints are rejected, while adjacent intervals are accepted. Proposed implementation default: preserve adjacent intervals separately and return same-day intervals in opening-time order. Overnight periods are represented as two same-day-local intervals split at midnight; the API normalizes an input such as Friday 22:00–02:00 into Friday 22:00–24:00 and Saturday 00:00–02:00, with Sunday wrapping to Monday, then validates overlap. No `business_hours` row means no configured schedule; a row with no intervals means a configured all-closed week. API `hours:null` clears the row and intervals, and a supplied seven-day schedule replaces them atomically. There is no holiday or open-now column. `business_hours.timezone` must equal the Business timezone in the same content transaction; changing timezone validates the retained/supplied schedule and increments the content revision.

### `business_images`

One current row exists per Business and role (`logo` or `cover`).

| Column | Type | Constraint / meaning |
|---|---|---|
| `id` | `uuid` | Primary key |
| `business_id` | `uuid` | Required FK |
| `role` | `text` | `logo` or `cover` |
| `storage_object_key` | `text` | Required server-generated immutable private-object key |
| `mime_type` | `text` | `image/jpeg`, `image/png`, or `image/webp` |
| `byte_size` | `integer` | 1–2,097,152 |
| `width` / `height` | `integer` | Positive; product ≤ 16 megapixels |
| `sha256` | `bytea` | Sanitized-object digest |
| `created_at` | `timestamptz` | Object/reference creation time |
| `replaced_at` | `timestamptz` | Nullable |
| `is_current` | `boolean` | Required |

Unique `(business_id, role) where is_current` enforces one current reference. Storage is private; `storage_object_key` never enters public projections. A public image request checks current Business eligibility and the current row before delivery. Replacing/removing a reference increments the Business content revision. Object storage and PostgreSQL are not one transaction: register a server-owned upload intent before storage, validate and sanitize the immutable private object, then commit the reference. The same reference transaction marks the former row noncurrent, sets `replaced_at` (also on removal), and records an immediate cleanup candidate. After commit, new requests for the former image identity fail the current-reference gate, including HEAD and conditional requests; physical retention grants no public access. Already delivered or in-flight copies cannot be recalled. Cleanup is separate and idempotent and never deletes an object still referenced by any current row.

### `card_history`

Append-only, lifetime operational history is separate from routine audit and analytics.

| Column | Type | Constraint / meaning |
|---|---|---|
| `id` | `uuid` | Primary key |
| `card_id` | `uuid` | Required FK to `cards`, `RESTRICT` |
| `event_type` | `text` | `created`, `imported`, `assigned`, `reassigned`, `activated`, `deactivated`, or `unassigned` |
| `actor_user_id` | `uuid` | Required Admin identity; every creation/import event is attributed to the initiating verified Admin |
| `occurred_at` | `timestamptz` | Database event time |
| `old_status` / `new_status` | `text` | Nullable only for creation/import old state; valid lifecycle values |
| `old_business_id` / `new_business_id` | `uuid` | Nullable assignment before/after |
| `mutation_id` | `uuid` | Required transaction/correlation identifier, unique per successful event |

Only actual state or assignment changes create lifecycle rows. Skipped existing imports, no-ops, stale writes, validation failures and rejected commands do not. There are no IPs, actor email copies, content snapshots, Visitor events or reason text. Database permissions and an append-only trigger prevent update/delete by application roles. The per-Card Admin timeline is read-only and retained for the permanent Card lifetime.

### `admin_audit_events`

Routine minimized audit metadata is retained 90 days. It is not a substitute for Card history.

| Column | Type | Constraint / meaning |
|---|---|---|
| `id` | `uuid` | Primary key |
| `actor_user_id` | `uuid` | Admin identity |
| `event_type` | `text` | Registered mutation/security event |
| `resource_type` / `resource_id` | `text` / `uuid` | Optional affected resource |
| `mutation_id` | `uuid` | Correlates one committed mutation |
| `request_id` | `text` | Opaque request reference |
| `created_at` | `timestamptz` | Database event time |
| `metadata` | `jsonb` | Minimized allow-listed metadata only |

Do not store raw tokens, request bodies, secrets, IP addresses, session tokens, or copied actor emails. Successful data mutation, audit, and required Card history use one transaction; audit failure rejects the mutation. Rejected attempts may be recorded separately as minimized security audit but never as successful Card history.

### `idempotency_records`

This durable table binds retries to an authenticated Admin and exact request payload.

| Column | Type | Constraint / meaning |
|---|---|---|
| `id` | `uuid` | Primary key |
| `scope` | `text` | Operation namespace, e.g. `admin.cards.activate` |
| `actor_user_id` | `uuid` | Authenticated Admin; replay authorization is rechecked |
| `key_digest` | `bytea` | Hash of the supplied key; never store the raw key |
| `request_digest` | `bytea` | Canonical payload/target hash |
| `state` | `text` | `processing`, `committed`, or `failed` |
| `response_status` | `smallint` | Stored committed HTTP status |
| `response_body` | `jsonb` | Redacted original result, no secrets |
| `resource_version` | `bigint` | Resulting aggregate version when applicable |
| `created_at` | `timestamptz` | Start time |
| `expires_at` | `timestamptz` | Retention deadline |
| `completed_at` | `timestamptz` | Nullable |

Unique `(scope, actor_user_id, key_digest)` prevents duplicate effect. A same key with a different request digest returns a stable conflict and performs no mutation. Proposed implementation default: retain completed records for 24 hours, processing records for 30 minutes, and keep no failed response beyond 24 hours; these are operational defaults, not settled product/security policy. Expiry is a deletion job that must not remove a processing record. The mutation and its committed idempotency result are written atomically; response replay never reruns the command. After expiry, a retry is a new request subject to current expected-version and lifecycle checks.

### `import_previews` and `temporary_objects`

`import_previews` stores a server-bound digest and parsed validation summary for the 30-minute preview window. It contains no authority by itself. Raw CSV bytes are private temporary data and expire within 24 hours. `temporary_objects` tracks upload intent, actor, Business, image role, immutable object key, digest, validation state, expiry and consumption time. Commit rechecks Admin/MFA, expiry, digest, row validation and uniqueness. Image completion locks the intent and parent Business and consumes an unused, unexpired intent in the reference transaction. Cleanup locks and expires an unused intent before deletion so completion cannot race deletion. These records are operational staging data, not backups.

Proposed implementation default: `image_cleanup_candidates` records the immutable object identity, former image row, `eligible_at`, `cleanup_due_at`, completion time and minimized retry state. Reference replacement/removal inserts this record atomically with the current-reference change; `eligible_at` is the commit transition time and `cleanup_due_at` is seven days later. Candidates cannot be reattached as current images. Maintenance checks no current reference uses the object before deletion, treats an already missing object as success and retries provider failures with redacted alerts. No age-only bucket sweep is permitted. These physical records implement the upload-intent and cleanup workflow in [ARCHITECTURE.md](ARCHITECTURE.md#recommended-private-image-workflow), not a new queue service.

## Public projections and indexes

Public reads use a restricted database view/function or equivalent server projection. It includes only an Enabled Business's public identity fields, enabled Sections/settings in configured order, active Links in their enabled Section's configured order, canonical contact/location/review content and normalized hours only for their enabled Section, and opaque gated image references. It excludes internal UUIDs where not needed, Admin identities, Card inventory/history, audit, raw storage keys, disabled/hidden Section content, inactive Links and unpublished data. Management tables are not anonymously readable. Hidden Section content and inactive Links have no fallback rendering path.

Required indexes:

- Unique `cards(public_token)` using the exact token comparison; `cards(business_id, status, id)` for Admin and eligibility lookup.
- `businesses(status, id)` and `businesses(updated_at, id)` for stable Admin lists.
- `business_slugs(business_id, is_current)` and lookup by primary `slug`.
- `business_sections(business_id, is_enabled, sort_order, id)` and unique `(business_id, section_type)`.
- `business_links(business_id, section_id, is_active, sort_order, id)`.
- `business_images(business_id, role) where is_current`.
- `business_hour_intervals(business_id, weekday, sort_order)`.
- `card_history(card_id, occurred_at desc, id desc)`.
- `admin_audit_events(created_at)` and `(resource_type, resource_id, created_at)`.
- `idempotency_records(scope, actor_user_id, key_digest)` unique and `expires_at` for cleanup.

Cursor pagination uses stable `(created_at or updated_at, id)` ordering and opaque cursors; exact API bounds belong to [FLOWS_AND_API.md](FLOWS_AND_API.md).

## Versioning and content revisions

`edit_version` protects the aggregate being edited. The API must include the version read by the Admin; SQL updates use `where id = ? and edit_version = ?`, and zero affected rows produce a conflict with no partial mutation.

`businesses.content_revision` identifies the public representation and starts at `1`. The following advance it exactly once in the same transaction as the Business edit: public scalar fields, contact fields, timezone/hours, Section enabled/settings/order changes, Link add/edit/remove/order, image reference add/replace/remove, and current-slug changes. Card assignment, activation, audit-only changes and Admin membership changes do not advance it. The revision is not required to equal `edit_version`.

A coherent public read obtains the fresh eligibility row and revision, then loads the restricted projection in one repeatable statement/snapshot or verifies the revision again before returning it. If the revision changed during load, retry once using the new revision or fail closed. Cache keys include environment, Business UUID, content revision, renderer version and schema version. No public cache is selected before the fresh gate. Cache-write failure does not fail a valid read.

## Transaction boundaries

### Card lifecycle transaction

Within one database transaction: lock the Card row, verify expected version and lifecycle, update Card state/assignment/timestamps/version, insert one `card_history` row when state/assignment changes, insert minimized successful audit, and insert/update the idempotency record if applicable. Commit all or none. Deactivate-before-reassign is enforced by the state check. Activation may occur while the Business is Disabled. No external cache purge is required for correctness; the next request performs the fresh gate.

### Business/content transaction

Within one transaction: lock Business, verify expected version, validate same-Business children and registered schemas, update content rows, increment `edit_version`, increment `content_revision` when public data changed, and insert required audit. Enablement checks nonempty name and unique current slug; disable changes publication state but leaves Card rows and assignment unchanged. Commit all or none.

### Slug transaction

Lock the Business and slug registry, verify expected version, reserve the normalized new slug, retire the prior current row, mark the new row current, update the Business version/revision, and audit. A uniqueness conflict aborts the complete change. Historical aliases remain permanently tied to the original Business.

### Import transaction

Preview is read/temporary-only. At commit, revalidate the preview and insert all new Cards as Inactive/unassigned, attribute each `imported` history row to the initiating verified Admin, and write one audit/idempotency result. Existing exact tokens are skipped unchanged. Any invalid row or in-file duplicate aborts the entire batch; no partial insertion occurs. CSV is UTF-8, max 10,000 rows and 10 MiB, with optional status allowed only as Inactive.

### Image transaction boundary

Object storage upload and PostgreSQL are intentionally separate. Register an upload intent before storage, store a validated sanitized immutable private object, then commit the current `business_images` reference, consumed intent, former-object cleanup candidate, Business version/revision, audit and retry result transactionally. Before-commit failure leaves the old reference current. Removal uses the same transaction without a new object. After commit, old-image access is revoked immediately for every new request by current-reference gating, independent of physical deletion. Replaced/removed objects are eligible for cleanup immediately; there is no seven-day access or minimum-retention grace. Proposed implementation default: physical deletion is due no later than seven days after reference replacement/removal. Cleanup is idempotent, checks all current references and never deletes the current object; overdue/provider failures remain retryable and observable rather than reported as rollback or successful deletion. Raw imports and unused temporary objects expire within the accepted 24 hours; committed replaced/removed objects use the separately labeled seven-day maximum cleanup deadline. Actual maintenance/deletion capability remains an external provider verification gate, consistent with Architecture.

## Migrations, retention and restore

Use reviewed, versioned Supabase SQL migrations in source control. Apply and test migrations in staging before production; prohibit undocumented dashboard-only production schema edits. Migration rules:

1. Add nullable columns/tables and backfill in bounded steps.
2. Validate legacy values before adding `not null`, enum/check, or uniqueness constraints.
3. Never rewrite printed Card IDs, normalize them, reuse them, or discard Card history/slug reservations.
4. Add indexes concurrently where supported and record the migration version.
5. Keep forward and rollback/data-repair notes; destructive changes require an explicit retention and restore review.

Retention defaults and settled periods are:

| Data | Retention |
|---|---|
| Card history | Permanent Card lifetime |
| Routine minimized Admin audit | 90 days |
| Redacted operational errors | 14 days |
| Raw imports and unused temporary objects | 24 hours |
| Import preview | 30 minutes |
| Idempotency records | 24 hours proposed implementation default |
| Replaced/removed image objects | Immediately inaccessible and eligible for deletion after reference commit; physical deletion due within 7 days, proposed maximum cleanup-deadline default, not a public-access or minimum-retention grace |

Provider-native logs, Auth records, Storage versions, backups, schedules, deletion, regions, RPO/RTO and recovery targets are not inferred from these application periods. Before launch, verify provider capabilities and perform a restore exercise covering relational data and private image objects. Hold public delivery while reconciling post-snapshot revocations, Business status, Card assignment/status, slug reservations, content revisions, audit/history and current image references. Do not reopen routes merely because a database restore succeeded.

## Genuine gates and implementation defaults

The actual legacy Card inventory/sample is absent. This is a factual prelaunch gate: inspect real printed tokens before import or manufacture compatibility testing, and verify grammar, case handling, URL parsing and practical entropy. The design intentionally preserves every imported token exactly and does not claim that the sample tokens in `vision.md` describe production inventory.

The Cloudflare Workers Next.js adapter, Supabase provider-native log/backup behavior, runtime enforcement of RLS/MFA/session limits, image decoding/delivery compatibility, and numerical operating/recovery targets remain gates owned by [ARCHITECTURE.md](ARCHITECTURE.md) and [SECURITY_AND_EDGE_CASES.md](SECURITY_AND_EDGE_CASES.md). No values here waive those checks.

The following are clearly labeled implementation defaults, not reopened product/security choices: binary-safe exact token comparison; the slug grammar and normalization described above; canonical location/review columns; schema-v1 Section settings and Link/icon registries; Unicode/contact/label normalization and compact UTF-8 settings byte counting; complete member ordering independent of visibility; UTC database timestamps with IANA display timezone; ISO weekday and minute-based hours split at midnight; 24-hour idempotency retention; immediate replaced/removed-object cleanup eligibility with a seven-day maximum physical-deletion deadline; upload-intent/cleanup-candidate persistence; repeatable-snapshot public projection with one revision retry; and database-trigger/privilege enforcement for append-only history. Each default may be replaced during implementation if the settled boundaries and companion contracts remain intact.
